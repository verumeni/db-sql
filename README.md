# PostgreSQL学習ロードマップ

## 学習目的
- 実行計画を根拠に、遅いSQLを改善できる力を身につける。
- インデックス設計とトランザクション制御を、性能改善の文脈で実践できる状態を目指す。

## 前提条件
- 対象DBは PostgreSQL（InnoDB前提の内容は含めない）。
- 目的は資格対策より、実務での遅いSQL改善力の向上を優先する。

## 学習ステップ

### Step 1: 実行計画の読み方の土台
- テーマ: `EXPLAIN` / `EXPLAIN (ANALYZE, BUFFERS)` を正しく読む。
- 学習内容:
  - 実行計画ノード（Seq Scan, Index Scan, Nested Loop, Hash Join など）の意味を理解する。
  - 見積もり行数と実測行数の差から、統計や条件の問題を見つける。
- 週次成果物:
  - 3クエリ分の実行計画読解メモ（遅い理由の仮説付き）。

### Step 2: インデックス基礎（B-Treeと選択性）
- テーマ: インデックス有無で実行計画がどう変わるかを把握する。
- 学習内容:
  - 単一/複合インデックスと選択性の関係を理解する。
  - WHERE句・ORDER BY・JOIN条件とインデックスの効き方を確認する。
- 週次成果物:
  - インデックス追加前後の計画比較を3ケース作成する。

### Step 3: クエリ改善の反復
- テーマ: SQL書き換えとインデックス設計を組み合わせて改善する。
- 学習内容:
  - 不要な全件走査や過剰なソートを減らすためのクエリ書き換えを行う。
  - 改善優先順位を「走査行数削減 -> I/O削減 -> ソート削減」で判断する。
- 週次成果物:
  - 遅いSQL 5本の改善ログ（変更理由と再計測結果付き）。

### Step 4: トランザクション基礎
- テーマ: ACIDとMVCCの理解を実行結果で確認する。
- 学習内容:
  - 分離レベルの違いが読み取り結果に与える影響を検証する。
  - `READ COMMITTED` と `REPEATABLE READ` の挙動差を再現する。
- 週次成果物:
  - 分離レベル別の挙動比較ノート。

### Step 5: ロック競合とデッドロック
- テーマ: 競合を再現して原因を説明できるようにする。
- 学習内容:
  - 行ロック競合とデッドロックの発生条件を2セッションで再現する。
  - ログとシステムビューから待機原因を追跡する。
- 週次成果物:
  - 競合再現手順書（原因、再現SQL、回避策付き）。

### Step 6: 高度なインデックス設計
- テーマ: 読み取り性能と更新コストのトレードオフを設計判断できるようにする。
- 学習内容:
  - 複合インデックスの列順と用途を設計根拠付きで説明する。
  - 不要インデックスや過剰インデックスの悪影響を把握する。
- 週次成果物:
  - 3テーブル分のインデックス設計レビュー（採用/不採用理由付き）。

### Step 7: 実務寄りチューニング演習
- テーマ: ボトルネック特定から改善までを一連で実施する。
- 学習内容:
  - 遅いクエリ候補を抽出し、改善対象を優先順位付けする。
  - 改善案ごとに実行計画と実測時間で効果検証する。
- 週次成果物:
  - Before/Afterの数値付き改善レポート1本。

### Step 8: 総合演習（ミニ改善プロジェクト）
- テーマ: 実行計画・インデックス・トランザクションを統合して改善する。
- 学習内容:
  - 複数の遅いSQLに対して診断 -> 改善 -> 再計測を通しで実施する。
  - 競合リスクを含めた安全な変更手順を整理する。
- 週次成果物:
  - 最終成果物として「診断手順テンプレート」と「改善チェックリスト」を作成する。

## 実行環境（Docker）
- 前提ディレクトリ構成:
  - `db-sql/`
  - `compose.yaml`
  - `postgres/postgresql.conf`
  - `postgres/init/`
- `compose.yaml` では `./postgres/init` をコンテナ側 `/docker-entrypoint-initdb.d` にマウントする。
- `postgresql.conf` の主な有効化項目:
  - `shared_preload_libraries = 'pg_stat_statements,auto_explain'`
  - `log_min_duration_statement`
  - `log_lock_waits`
  - `deadlock_timeout`
- 拡張機能はDB単位で有効化するため、対象DBで次を実行する。

```sql
CREATE EXTENSION IF NOT EXISTS pg_stat_statements;
```

- `init` の挙動:
  - `/docker-entrypoint-initdb.d` はファイルではなくディレクトリ。
  - 初回起動時（PGDATA未初期化）にのみ `init` 内SQLが実行される。
  - 判定の目安は `PGDATA/PG_VERSION` の有無。

## 到達判定（完了基準）
- 初見の遅いSQL 3本に対して、30-60分で改善案を提示できる。
- 3本中2本以上で、Before/Afterの実測時間短縮を示せる。
- ロック競合またはデッドロックを1件以上再現し、原因と回避策を説明できる。
- 実行計画・インデックス・トランザクションの3領域を、同等の比重で説明できる。

## 学習ログテンプレート
- 次の形式で毎回記録する。

```text
現象 -> 実行計画 -> 仮説 -> 変更 -> 再計測 -> 採否
```

- 記録例:

```text
現象: API一覧取得が1.8秒かかる
実行計画: ordersをSeq Scan、rows見積もりが実測と乖離
仮説: user_id + ordered_atの複合インデックス不足
変更: CREATE INDEX idx_orders_user_ordered_at ON orders(user_id, ordered_at DESC);
再計測: 1.8秒 -> 220ms
採否: 採用（更新コストの増分も許容範囲）
```
