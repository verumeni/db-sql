# Step1: 詳細解説

## 実践ガイド
- 目的: 3つの代表クエリで「計画を読む -> 遅い理由を仮設化 -> 改善案を出す」を練習する。

```bash
# PostgreSQL db接続コマンド
psql -h {host} -p {port} -U {user} -d {db}
```

### 実行計画の読み方
- 実行計画はツリー構造となっており「->」で階層を表す
- 基本的には階層が深いところから実行されていくため以下のルールで読む
  1. 子要素をたどり1番子孫の要素から親要素へさかのぼっていく(右から左)
  2. 同じ階層同士の場合は先に記述されている行から順に子要素をたどる(上から下)
- ノードごとの見方(Seq Scan on orders o  (cost=0.00..5861.00 rows=300000 width=38) (actual time=0.316..0.318 rows=20 loops=1))
  - `Seq Scan` 演算子, コストがかかるものとかかりにくいものがある
  - `cost=0.00..5861.00` 処理の重さ, 左が初期コスト(0.00), 右がトータルコスト(5861.00)
  - `rows=300000` 対象行数
  - `width=38` データサイズ
  - `actual` 実際に実行された情報
    - `loops` 処理の繰り返し回数
    - `time` 実行時間
- プランを見るポイント
  - 演算子
  - トータルコスト
  - 実行時間
  - プランと実際の実行結果に乖離があるか(rows と actual rowsの乖離など)

### プラン演算子
- テーブルスキャン演算子
  - `Seq Scan` テーブルを最初から最後までアクセス(フルスキャン)
    - 多くの行を読み込む必要がある場合はインデックススキャンよりもフルスキャンの方がいい場合もある
    - 数件の結果を取得するような場合にフルスキャンで読み込みが発生している場合は注意
  - `Index Scan` インデックスを利用したアクセス
    - 少数行を探す場合に有利
- 結合で使用する演算子
  - `Nested Loop join` 外側テーブル1行ごとに内側テーブルを1周ループしながら結合する方法
  - `Merge Join` 2つのテーブルを結合キーでソート後、順番に付き合わせて結合する方法
  - `Hash Join` 一方のテーブルから作られたハッシュ表を元に結合を行う方法
- その他
  - `Sort演算子`

 ### コストが高くなりがちな項目

 ### テーブル結合時
- Nested Loop Join -> 少量 + 内側インデックス
- Hash Join -> 大量結合
- Merge Join -> 大量結合 + ソート利用

結合プランを正しく適用することで結合コストを抑える

### 1.Nested Loop Join

片方の表を1行ずつ読み、都度もう片方の表から一致行を探す方式<br>
右側表をインデックスで探せるなら有効 (左表 => outer, 右表 => inner)

### 向いている場面
- 外側の表の件数が少ない (外側 => outer, 内側 => inner 結合処理において先に取り出す側がouter)
- 内側の表に結合キーのインデックスがある
- 先に絞り込める
- 先頭行を返却したい

内側表の走査量が少なければ Nested Loop が有利

### 苦手な場面
- 外側表から大量の行が流れてくる
- 内側表を何度も探しに行く必要がある
- ランダムアクセスが多い

外側表の件数が多いと内側表の検索を回数が増えるためコストが高くなりやすい<br>
内側表のインデックス参照が効いていれば速く処理できる

### 2.Hash Join

一方の表を先に読んで結合キーを使ってハッシュテーブルを作成<br>
その後もう一方の表を読みながら一致を探す

### 向いている場面
- 結合対象が多い
- インデックス経由で1件ずつ探すより、一括処理の方がよい
- 等価結合が中心 (内部結合)
- 中規模 ~ 大規模の結合

Nested Loop は読み込む行数が少ないときに有利だが Hash Join は行数が多い場合に有利

### 苦手な場面
- ハッシュテーブルを作るためにメモリを消費
- メモリ不足で一時的領域退避が発生
- 少量検索なのに向いていない

メモリが必要なためリソースコストが高い

### 3.Merge Join

両方の入力が結合キー順に並んでいる前提で先頭から突き合わせていく方式

### 向いている場面
- 両側が既にソート済み
- インデックス順走査で順序を利用できる
- 大量データ同士の結合
- 不等号条件を含む場面でも有利になることがある

### 苦手な場面
- 両方をソートしないといけない
- ソートコストがかかる
- 少量データでは準備コストが過剰
